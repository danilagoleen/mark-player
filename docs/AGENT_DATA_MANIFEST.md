# Манифест данных Mark Player для агента

Как агенту без GUI, одними файлами, положить ШТАТНЫЕ маркеры плеера
(in/out, комментарии) для видео — чтобы их увидели и плеер, и Premiere.

Протокол: этапы 6, 7, 11 — `docs/218_ph_CUT_CATALOG/CUT_PRODUCTION_PROTOCOL_2026-10-09.md`.
Живой манифест кнопок: `window.vetkaPlayerLab.manifest()` в запущенном плеере.

**Правило №1.** Агент сначала ищет готовый инструмент в этом документе.
Новый формат — только через Альфу: новое поле должны увидеть и плеер,
и Premiere (протокол §4 п.1).

**Запустить плеер и показать момент — одна команда.** Оператор сказал
«запусти плеер» / «покажи моменты» / «open the player» — искать в интернете
нечего: §0.3 `{#hpdm-playerctl}`,
`python3 player_playground/scripts/player_ctl.py launch`.

## 0. Что такое штатные маркеры <!-- {#hpdm-s0} -->

Виды: `favorite` (★), `negative` (✗), `in` (⇒), `out` (←),
`comment` (·), `chat` (·). Пара `in` + `out` = скобки фрагмента, их сумму
считает плеер. Время — СЕКУНДЫ от начала файла (в SRT — `HH:MM:SS,mmm`).

**Скобки и черта — два разных инструмента** (слово оператора 17.11):
скобки `in` / `out` — выбор видео в монтаж; черта вопроса `qmat_<qid>_in` /
`_out` — подчёркивание участка в опросе агента. Подробно — §5,
`{#hpdm-brackets3}`.

Честно: плеер НЕ подбирает файлы-спутники сам при открытии видео.
Импорт — явный: меню File → Import или вызов `window.vetkaPlayerLab`
(см. §3). Файл, просто лежащий рядом с видео, маркеров не даст.

## 0.2. Карта «поле записи → где это видит оператор» <!-- {#hpdm-fieldmap} -->

Проверяя показ, агент сверяется с этой таблицей, а не с догадкой. Случай
16.11 ([task:tb_1794846994_51008_1]): Commander написал оператору «в строке
гипотеза у каждого шота стоит, что думает модуль» — а такой строки в
карточке не было, `hypothesis` светилась только всплывающей подсказкой;
мнение модуля пришлось вписать в название записи, и оператор искал «гипотезу»
в списке. Окна плеера: **Playlist** (список записей), **карточка** (вопрос,
поле комментария, кнопки ответов), **кадр** (титр поверх видео), **шкала**
(скобки и маркеры), **Markers** (окно маркеров).

| Поле записи | Где это видит оператор | Заметка агенту |
|---|---|---|
| `name` | заголовок строки списка Playlist, одной строкой (длинное режется) | коротко: номер + файл + суть. Мнение модуля сюда не класть: это название строки списка, а не карточка |
| `question` | заголовок карточки (до 4 строк); серая строка записи в списке | что именно отметить |
| `hypothesis` | строка «Module: …» в карточке под вопросом (с 0.26.12, до 3 строк, полный текст в подсказке); в списке — только подсказка при наведении | что думает модуль: числа и классы, без градусов и подсказок ответа |
| `caption` | титр поверх кадра на `in_sec`..`out_sec` записи (§5.6) | факт о кадре: файл, участок, версия |
| `choices` | кнопки ответов в карточке вместо Confirm / Reject / Not sure | ответ несёт выбранный `choice` |
| `in_sec`, `out_sec` | ЧЕРТА вопроса: ровная линия над дорожкой на отрезке in..out (не скобки `[` `]`); ответ принимается только внутри неё | секунды, не таймкод |
| `duration` | время под названием строки списка; нет поля — строки времени нет (с 0.26.12 без «NaN:NaN») | секунды, по возможности давать |
| `bbox`, `bbox_end` | рамка на кадре, пока запись активна | доли кадра |
| `markers[]` | маркеры-подсказки агента на шкале и в окне Markers (автор `agent:<роль>`) | комментарии, ≤ 80 символов в имени |
| `path` | какой файл откроется (прокси ≠ исходник) | точный путь |

Окно Markers: иконка 💬 и клавиша M открывают его с фильтром «только
комментарии». Если на файле лежат маркеры вопроса (`qmat_*`), окно открывается
со всеми маркерами (с 0.26.12): оператор в плейлисте агента ставит ★/✗
клавишами N/F и тулбаром. Всё, что скрыто фильтром, окно называет строкой
«N hidden by the filter (★ 1 · ✗ 2) — show all» с кликом.

## 0.3. Как агенту открыть плеер: одна команда <!-- {#hpdm-playerctl} -->

[task:tb_1794852208_51008_1] Раньше на «запусти плеер» агент искал в сети, что
это такое. Теперь есть кнопка REFLEX `vetka_player_ctl` (зарегистрирована
`scripts/release/add_tool.sh`, ищется по словам «плеер», «запусти плеер», «покажи
моменты», «player», «open player», «play range») и скрипт без зависимостей
`player_playground/scripts/player_ctl.py`. Он кладёт команду в `inbox/` (§5.5),
ждёт `ack/` и печатает ответ.

```
python3 player_playground/scripts/player_ctl.py launch
python3 player_playground/scripts/player_ctl.py --by Beta play_range --file /Volumes/x/clip.mov 812.4 819
python3 player_playground/scripts/player_ctl.py --by Beta open_playlist --inline questions.json
python3 player_playground/scripts/player_ctl.py read_answers --cmd <id из вывода open_playlist>
python3 player_playground/scripts/player_ctl.py status
```

Глаголы: `launch`, `status`, `open_file`, `open_playlist` (путь или `--inline`),
`seek`, `play_range` (с `--file` сначала откроет файл), `pause`, `next`,
`read_answers` (`--cmd <id>` или `--playlist <путь>`). `--by` — ваша роль.

Правила, на которых скрипт не уступает:

- **`launch` запускает приложение сам** (`open "/Applications/Mark Player.app"`,
  путь, а не `-a`) и прямым текстом пишет: «started» или «already running», pid и
  `player_version`, которая ответила; если запущенная сборка не равна
  установленной — строка `WARNING` (ловушка §5.5.2).
- **Остальные глаголы без плеера отказывают** кодом 4 с текстом «сначала
  launch», а не кладут команду в `inbox/`, который никто не читает.
- **Чужую копию** (другой путь, например сборка из `src-tauri/target`) скрипт не
  убивает и вторую не запускает: код 5, просьба к оператору её закрыть.
- **Нет ack за таймаут** (`--timeout`, по умолчанию 20 с; у `launch` 45 с) —
  код 6 и фраза, что команда лежит в `inbox/` без ответа; у команды `expires_at`
  через таймаут+5 с, поздно она не сработает.
- Коды: 0 ок, 2 неверные аргументы, 3 плеер ответил `error`/`expired`, 4 плеер не
  запущен, 5 запущена чужая копия, 6 нет ack, 7 приложение не стартовало, 8 файла
  ответов ещё нет.

Честно: `done` — это «команда исполнена», а не «человек видит вопросы»; что
проверить кроме ack — §5.5.2. Путь данных и приложения переопределяются
`MARK_PLAYER_DATA_DIR` и `MARK_PLAYER_APP` (для тестов и нестандартных установок).

## 1. Путь А: SRT-файл маркеров (самый простой)

Формат — тот же, что пишет сам плеер (Export → Current Video →
Subtitles (SRT)…): номер, время, строка `ГЛИФ label | text`.

```srt
1
00:00:12,500 --> 00:00:12,500
⇒ заминка 3

2
00:00:14,000 --> 00:00:18,000
· спорное место | проверить по расшифровке

3
00:00:18,000 --> 00:00:18,000
← заминка 3
```

Глифы: `★ favorite`, `✗ negative`, `⇒ in`, `← out`, `· comment/chat`.
Точечный маркер — нулевая длительность (`start == end`).
Импорт: File → Import → Subtitles (SRT)… (или
`vetkaPlayerLab.importSubtitlesText(text, mediaPath)`), затем подтвердить
«создать маркеры». Эвристика плеера: если ≥50% строк начинаются с глифа —
это SRT маркеров, а не субтитры (`looksLikeMarkers`). Кодировка: UTF-8,
иначе cp1251. Повторный импорт заменяет дорожку целиком.

## 2. Путь Б: Markers JSON / sidecar `.sos.json`

Sidecar (`sos_version: "0.3"`, пишет Export → Markers (JSON/SOS)…):

```json
{
  "sos_version": "0.3",
  "source": "cut_player",
  "media_path": "/idx/P1755050.mov",
  "content_hash": null,
  "generated_at": "2026-10-09T00:00:00.000Z",
  "markers": [
    { "marker_id": "q03-in", "kind": "in", "start_sec": 12.5,
      "end_sec": 12.5, "anchor_sec": 12.5, "label": "заминка 3", "text": "" },
    { "marker_id": "q03-c1", "kind": "comment", "start_sec": 14.0,
      "end_sec": 18.0, "anchor_sec": 16.0, "label": "спорное место",
      "text": "проверить по расшифровке" }
  ],
  "provisional_events": []
}
```

Импорт принимает и короткий массив `[{kind, text|label, anchor_sec|time,
start_sec, end_sec}]` — лишнее отбрасывается, неизвестный `kind` становится
`favorite` (`normalizeImportedMarker`). Импорт: File → Import →
Markers (JSON)…. Привязка к видео — по `media_path` (копия/переименование
находится по `content_hash`, `null` = хеш неизвестен, честно).

Точные имена файлов экспорта (UPD 13.10, [task:tb_1791907340_49359_1]):
Export → Current Video → Markers (JSON/SOS)… пишет `<имя>.sos.json`
(по имени текущего видео; `App.tsx:performExportJson`). Export → Playlist →
Markers (JSON/SOS)… пишет `<имя плейлиста>.markers.json`
(`App.tsx:3102`). Кнопка Export окна Playlist пишет `<имя>.json` + рядом
sibling `<имя>.json.answers.json` (с 0.25.74, [task:tb_1791885959_77379_1]).
`_export` в именах вроде `Orientation_check_v1_export.json` — НЕ суффикс
кода, а часть имени, которое дал плейлисту агент: код пишет
`<sanitized playlist name>.json` как есть.

## 3. Как плеер подхватит (без GUI — никак, нужен один шаг человека или API)

Варианты: (а) оператор открывает видео и жмёт File → Import → …;
(б) агент в десктопе вызывает `vetkaPlayerLab.importSubtitlesText(text,
mediaPath)` — `mediaPath` обязан совпадать с открытым файлом, иначе тост
«open a video first». После импорта маркеры — штатные: видны на шкале,
в окне Comments, едут в экспорт.

## 4. Как маркеры уходят в Premiere

- Timeline (XML)… — маркеры файла с цветами видов (comment/note/chat —
  синий, favorite — зелёный, negative — красный; ABGR, проверено глазами
  в Premiere 24.09). Частота кадров — честная (`resolveXmlFps`:
  container/probe/estimated/fallback — сверить настройки сиквенса).
- Markers (EDL, DaVinci)… — для DaVinci.
- Для плейлиста — те же пункты в Export → Playlist (пакет:
  XML + SRT + JSON + Review Notes + frames + `.editor/`).
- Сам JSON вопрос-плейлиста (§5) в Premiere не уходит; штатные маркеры,
  записанные при импорте (в том числе концы черты `qmat_*_in` / `_out`, они
  режут XML-клипы), уходят как обычно.

## 5. Плейлист-вопрос: импорт сразу пишет штатные маркеры <!-- {#hpdm-s5} --> (решение 10.10, работает с 0.25.34, [task:tb_1791654032_27281_1])

Агент отдаёт ОДИН JSON на все видео (`vetka.cut.question_playlist/1` —
схема в `QUESTION_PLAYLIST.md`): запись = путь + `question_id` + вопрос +
гипотеза + `in_sec`/`out_sec` + `markers`. Человек открывает файл в панели
Playlist — черта записи (`in_sec` / `out_sec`) и её маркеры СРАЗУ становятся штатными маркерами, без кнопок
и подтверждений (файл агента и есть подтверждение). `source.by` — имя
агента (станет автором `agent:<имя>`); без него автор — `agent:agent`:

- `in_sec` / `out_sec` → ЧЕРТА вопроса: пара `qmat_<qid>_in` + `_out` (в XML режут клипы, как ручные I/O);
- `markers` записи → комменты (`label` = вопрос, `text` = гипотеза + текст);
- автор всех — `agent:<роль>` из `source.by` (это и есть пометка «ИИ»);
- повторный импорт дублей не плодит (детерминированные id `qmat_<qid>_*`).

Эфемерных скобок больше нет: пунктира, скип-движка и кнопки
«Материализовать» (0.25.33) — тоже. Дальше всё штатно: окно Markers,
ответы кнопкой ↳, Export → Playlist → XML (подрезанные клипы
с комментариями в Premiere).

Правило резолва путей: плеер открывает `entry.path` как есть, без подмен
(прокси не конформит в исходник и наоборот). Коллизия имён (у прокси
и исходников одинаковые basenames) — на совести агента: клади точный путь.

### Черта и скобки (не путать) <!-- {#hpdm-brackets3} --> ([task:tb_1794800630_73214_1], [task:tb_1794865760_47995_3], слово оператора 16.11 и 17.11, плеер 0.26.12)

Хранение одно — штатные маркеры `in` / `out` (в XML они режут клипы). Но
инструментов ДВА, и их различает назначение, а не автор. Слов «скобки агента»
и «скобки оператора» как разных вещей нет: скобки одни, чьи бы руки их ни
поставили.

1. **Черта** — инструмент агента для опроса: подчёркивает участок, о котором
   спрашивает вопрос. Это `qmat_<question_id>_in` / `_out`, их кладёт
   плейлист-вопрос по полям записи `in_sec` / `out_sec`. Черта рисуется на шкале
   ровной линией над дорожкой на отрезке in..out — без знаков `[ ]`, штриховки
   и цвета. Карточка вопроса и кнопки ответов привязаны к ней: вне черты кнопки
   погашены. Черта спаривается ПО ИДЕНТИФИКАТОРУ вопроса (а не по позиции).
   **Оператор черту не ставит и не двигает** — в плеере её нельзя схватить.
   Черты вопросов, которых нет в загруженном плейлисте (старый плейлист на том
   же файле), в парах, ножницах и на шкале не участвуют.
2. **Скобки** — инструмент монтажа: выбор видео в монтаж. Штатные `in` / `out`
   (клавиши I / O): знаки `[ ]` в основном ряду шкалы, их сумма — хронометраж,
   гард «скобку внутрь закрытой пары ставить нельзя» действует только против
   пар скобок. Внутри черты вопроса (даже если черта — весь клип) скобки
   ставятся свободно. Скобки ставит человек; агент может положить обычные
   `in` / `out` штатными маркерами (§1–§4), и это те же скобки.
3. **In–Out Play (ножницы)** — РЕЖИМ просмотра: играть только внутри заданных
   границ. **В плейлисте опроса скобки оператора в ножницах НЕ играют, играет
   только черта активного вопроса.** Агент показывает конкретный участок и
   спрашивает о нём; смотреть монтаж по своим скобкам оператору там не нужно.
   Правило по порядку: (а) у файла есть черта активного вопроса — играет она
   одна (одинокий IN — до конца файла); (б) черты нет (нет вопроса, вопрос на
   весь файл, картинка, вопрос другого файла) — играют скобки, как обычно;
   (в) ни черты, ни скобок — сегментов нет. Черты неактивных вопросов не играют.
   **Отличие черты от скобок на OUT** ([task:tb_1795483216_27036_1], слово оператора
   24.11): ДЕРЖИТ только черта и только при ножницах ВКЛ. Дойдя до OUT черты, на
   которую ещё нет ответа (вердикт, комментарий или `operator_range`, то же правило,
   что у прогресса «Вопрос N/M»), плеер встаёт ровно на OUT и ждёт; ответ даёт
   продолжение (переход на следующую запись), Play пропускает вопрос без ответа.
   Скобки монтажа не держат никогда, при ножницах ВЫКЛ плейхед идёт дальше. Нового
   поля в плейлисте для этого нет: так ведёт себя каждая черта вопроса.

Что из этого видит агент:

- Черта вопроса — то, что агент положил сам; в `answers.json` она выражена
  полями `in_sec` / `out_sec` ответа (текущее положение маркеров; старые данные
  со сдвинутой чертой читаются как раньше).
- Пара скобок оператора внутри черты — это ОТВЕТ агенту, а не набросок монтажа.
  Она уходит в `answers.json` ОТДЕЛЬНОЙ записью `"origin": "operator_range"`:
  `marker_start_sec` / `marker_end_sec` — границы, `marker_id` /
  `marker_out_id` — id скобок IN и OUT, `verdict` формально `"comment"` (поле
  обязательное) и **оценкой не является**. Смысл пары («в фокусе», «не в
  фокусе», «брак») задаёт сам вопрос, а не плеер. Пара вне черт, одинокая
  скобка, пара старше вопроса и скобки с автором `agent:<роль>` агенту как
  ответ оператора не доставляются.
- Ответ оператора (reply-маркер) несёт диапазон ОТ СВОЕГО якоря (±0.5 с),
  а не копию диапазона родителя (раньше ответы тащили чужие `12.25–13.25`).
- Повторный импорт и самоисцеление карточки дублей не плодят: маркер черты —
  это слот `marker_id` + файл, а не текущее положение; сдвинутый маркер
  не «возвращается».

Что уходит наружу (слово оператора 17.11: пусть остаётся так): концы черты —
обычные штатные маркеры плеера. Они попадают в `markers_all.json` и режут
клипы в XML для Premiere (решение 10.10), через черту агент показывает
оператору участок. Убирать их из выгрузок нельзя без слова оператора: на них
держатся XML-клипы.

Как составлять плейлист с учётом этого: черта на весь клип (`in_sec = 0`,
`out_sec = длительность`) допустима и не мешает человеку отмечать участки
внутри. Если нужен ответ про участок, спрашивай про него в `question` и
получай границы из записи `operator_range`.

Не сделано (задачи отдельные, ждут слова оператора): набросок монтажа от
агента прямо в плейлисте-вопросе — у записи нет поля для скобок монтажа, а
человек должен легко двигать такие скобки-склейки; по слову оператора 17.11 сдвиг
обычных скобок на шкале раньше не удавалось сделать удобным. Черта при этом
остаётся только инструментом опроса и пользователем не редактируется.

## 5.1. Калибровка сцен для Беты (решение 11.10): новый плейлист штатными инструментами

Старые `camera_calibration.json` / `scene_proposals.json` — не плейлисты,
больше не отдавать (плеер 0.25.45 ел их transitional-мостом — мост остаётся

обычный вопрос-плейлист §5 (`vetka.cut.question_playlist/1`), собранный
только штатными средствами:

- запись = файл; `in_sec` / `out_sec` — черта вопроса (штатная пара in/out:
  в XML режет, как ручные I/O);
- ВСЕ вопросы — в поле `question` + штатными комментариями (`markers`
  записи: `label` = вопрос, `text` = гипотеза); survey-форматов не лепить —
  запрещено. Разрешённые штатные поля (с 0.25.52): `bbox` / `bbox_end` (см.
  ниже) и `label` ≤ 80 символов (длиннее плеер режет сам; имя маркера
  в Premiere обрезается на полуслове — держи коротким);
- регион-лицо: `bbox: {x, y, w, h}` в ДОЛЯХ кадра (x,y — левый верхний
  угол; всё 0..1, x+w ≤ 1, y+h ≤ 1), опционально `bbox_end` — рамка на
  `out_sec`. Канон — поля ЗАПИСИ; `bbox` внутри `markers[i]` tolerated
  (плеер подхватит из первого маркера, где есть — так лёг people_merges_v01).
  Плеер рисует рамку поверх кадра, пока активен вопрос, и
  линейно едет `bbox` → `bbox_end` за `in..out` (на узкой черте выглядит
  как трекинг). Мусор (вне 0..1, нулевой размер, вылезание за кадр)
  отбрасывается целиком — лучше без рамки, чем мимо лица. Честно:
  в Premiere рамка уезжает ТЕКСТОМ (`[region …]` в тексте in/out-маркера —
  в XMEML/EDL/SRT полей под геометрию нет);
- подпись поверх кадра: необязательное поле записи `caption` (строка).
  Плеер показывает её поверх кадра, пока плейхед внутри `in_sec`..`out_sec`
  записи, и прячет вне окна. Это НЕ SRT-дорожка и НЕ маркер-комментарий:
  в SRT-маркеры не подмешивается, в Premiere не уезжает (§5.6);
- вопросы и ответы живут в окне Comments. **Одна правда — маркеры**
  (решение 12.10, плеер 0.25.55, [task:tb_1791809796_24701_1]): ответ

  Confirm / Reject / Not sure, а у записи с `choices` — кнопка-вариант
  (с 0.26.7, см. §5.2.1) — пишет `[answer] choice: comment (verdict)`,
  свободный текст ↳ — тоже ответ, verdict `comment`). `answers.json` —
  НЕ второй писатель, а выжимка `answersFromMarkers` из маркеров: плеер
  пересобирает её при каждом ответе (имя — от пути плейлиста; без пути —
  запасной аутбокс). Поля выжимки берутся из маркеров: `t_sec` = точка
  ответа, `answered_at` = время создания ответа, `in_sec`/`out_sec` =
  текущее положение черты вопроса. UPD 17.11 [task:tb_1794865760_47995_3]:
  раньше здесь стояло «человек двигает их сам» — это больше не так, в плеере
  черту двигать нельзя (решение оператора 16.11, tb_1794800630_73214_1); старые данные
  со сдвинутой чертой читаются как раньше. Маркер вопроса несёт
  `question_id` полем. В выжимку идут только прямые ответы на `qmat_*`;

- три места, где лежат ответы оператора (UPD 13.10,
  [task:tb_1791907340_49359_1]): (1) reply-маркеры (`author` +
  `reply_to: qmat_<qid>_*`, формат — §6.2); (2) `<плейлист>.answers.json`

- `source.by` — имя агента (автор `agent:<имя>`, пометка «ИИ»).
- Дисциплина отдач: каждая ревизия агента — своя версионная подпапка

## 5.2. Сверка людей <!-- {#hpdm-s52} --> — капча плейлистом по Proxies/ (решение оператора 13.10, протокол §4 п.13)

Люди сверяются не видео с рамкой, а картинками: «тот же человек?» —
вопрос про лицо, не про время. Сцены и всё, где важно движение
(камера, заминки), — видеоопросом §5.1. Плееру новый режим не нужен:

- агент отдаёт обычный вопрос-плейлист §5 по `Proxies/`: запись = отрезок
  клипа (или картинка без `in_sec`/`out_sec` — §5.2.1), `in_sec`/`out_sec` =
  границы, `label` «Same person?»,
  `source.by` = `agent:<роль>`; вертикали — предповёрнутыми клипами
  (плеер не поворачивает, rotate только в CUT player); без вшитого текста;
- человек отвечает карточкой: Confirm = один человек, Reject = разные,
  Not sure = не знаю; следующая пара — штатный In–Out Play;
- обрезки лиц режет агент локально, по проверенным боксам; кадры не
  покидают машину.
- куда что класть (протокол §4 п.12–13): человеку — только `edit/calibration/`
  (то, что открывается в плеере); входы, ключи и разметка агента — `phi_runs/`.
  Капчи «20–25 вопросов вслепую» больше нет (слово оператора 13.10, протокол
  §4 п.3): калибрующий агент смотрит кадры и размечает сам, человеку — только
  спорное.

Требования к генератору слайдов — капча v2 (фидбек оператора по двум
прогонам people_captcha_v01, 12.10):

1. Слева сетка обрезков человека A, справа — B, сверху ID обоих.
   НОМЕР на КАЖДОМ обрезке (на квадрате, A1…An / B1…Bn) — чтобы
   в комментарии можно было сказать «A3 — не он».
2. Лица строго горизонтально по линии глаз. Вертикальные кадры
   доворачиваются ДО нарезки — и камерные вертикалки (rotation в
   метаданных), и айфон; лицо на слайде не лежит на боку и не завалено.
3. Обрезки крупнее, без пустот между ними; в нижней полосе слайда, где
   поверх кадра лежит таймлайн плеера, — ничего.
4. Фон ЧЁРНЫЙ (как тёмный интерфейс Premiere): белый фон глаз читает
   как материал.
5. Мало обрезков (1 с какой-то стороны) — честно: Not sure там нормальный
   ответ.
6. **Заголовок, вопрос и варианты ответа в картинку НЕ вшивать** (слово
   оператора 01.11: на слайде `noise_0c185b991f.png` сверху было вшито
   «Person or noise? person / noise / not_sure»). Пилюля плеера с иконками
   (★, ✕, [ ], комментарий) НЕПОДВИЖНА и лежит поверх верха кадра (двигается
   только карточка вопроса, но не пилюля), поэтому текст у верхнего края
   картинки оказывается под иконками: вшитый заголовок так и резался на
   полуслове (поправка 02.11: прежняя формулировка «пилюля двигается» была
   неверной). Он дело рук генератора слайдов, не плеера. Вопрос и так показывает карточка
   (`question`), варианты — её кнопки (`choices`, с 0.26.7 это единственный ряд
   ответов), подпись к кадру — необязательное `caption` (§5.6, внизу кадра). На
   картинке остаётся то, что карточку не заменяет: обрезки с номерами и ID
   людей (п. 1), имя исходника и таймкод.

Карточка вопроса следует за playhead и переключается при смене записи
(0.25.56, 0.25.70). **До 0.26.6 `question_id` ответа верить было нельзя:**
ответ уходил вопросу карточки при любом положении плейхеда (живой прогон
фото-капчи 31.10). С 0.26.6 правила — §5.2.1; сверять пару по `question_id`
можно.

### 5.2.1. Какому вопросу уходит ответ (плеер 0.26.6, [task:tb_1793480340_10647_1])

Живой прогон 31.10: один mp4 на 6 слайдов, вопросы лишь на трёх. Оператор
ответил на все слайды, а ответы со слайдов без вопроса легли на чужие вопросы
(один вердикт перевёрнут). Часть корня была в плеере, часть — в форме
плейлиста. Что делает плеер (протокол — `QUESTION_PLAYLIST.md`, раздел
«Какому вопросу уходит ответ»):

- ответ принимается только внутри черты вопроса карточки
  (`in_sec ≤ t ≤ out_sec`). Вне черты весь ряд кнопок ответа погашен,
  карточка пишет «Playhead is outside this question»; ответ на слайд
  без вопроса не записывается, а не ложится на соседний;
- плейхед вошёл в черту другого вопроса того же файла — карточка
  переключается. На общей границе окон (0–10 и 10–20, `t = 10`) текущий вопрос
  остаётся своим, дальше выигрывает начинающееся окно;
- запись БЕЗ `in_sec`/`out_sec` — вопрос на весь файл (картинка, короткий клип):
  карточка есть и на картинке; родитель ответа — маркер
  `qmat_<question_id>_whole` (комментарий в 0:00 с текстом вопроса), в ответе
  `in_sec`/`out_sec` нет;
- `in_sec`/`out_sec` в `answers.json` — текущее положение черты из маркеров `in`/`out`.
  Раньше `out_sec` брался из точки `in` и равнялся `in_sec`. Одинокий IN —
  `out_sec` в ответе не пишется;
- ножницы (In–Out Play): пока у файла есть черта активного вопроса, играет
  ТОЛЬКО она; скобки оператора в ножницах там не играют (они ответ, §5,
  `{#hpdm-brackets3}`). Дошёл до OUT последней записи — пауза на конце черты;
  play оттуда начинает плейлист заново (первая запись), а не уходит в щель.
  Дошёл до OUT черты без ответа — тоже пауза на OUT: ответ ведёт на следующую
  запись, Play пропускает вопрос; скобки так не держат, при ножницах ВЫКЛ плеер
  не держит;
- **один ряд ответов (0.26.7, [task:tb_1793558199_43420_2]).** Раньше в карточке
  были два ряда — варианты `choices` и Confirm / Reject / Not sure, а ответ
  писал только нижний. Теперь ряд один: у записи есть `choices` — кнопки это
  сами варианты, клик = сразу ответ (`verdict` + `choice`); нет `choices` —
  три кнопки Confirm / Reject / Not sure. `verdict` варианта: `confirm` →
  `favorite`, `reject` → `negative`, `not_sure` → `comment`, любой другой
  (`master`, `model`, `other`, `student` …) → `favorite`. **`choice` пишется
  всегда**, и у да/нет-вопроса тоже. У вопроса «Кто это?» содержание ответа —
  `choice`; `verdict` лишь различает «назвали» (`favorite`) и «не уверен»
  (`comment`). Ответ на такой вопрос без `choice`, записанный до 0.26.7, —
  «нет данных», не `other`. Формат `answers.json` и reply-маркера не менялся
  (подробнее — `QUESTION_PLAYLIST.md`, «Карточка: один ряд ответов»).

Как агенту составлять плейлист:

1. Черты одного файла в одном плейлисте не пересекаются, и каждое место,
   где ждут ответ, покрыто чертой. Слайд без черты — слайд без вопроса,
   ответа там не примут. Нужно ответить на все слайды — дай вопрос на каждый.
2. Картинки: ОДИН ВОПРОС = ОДНА КАРТИНКА (запись с `path` на картинку, без
   `in_sec`/`out_sec`). Не склеивать слайды в одно видео ради плейлиста:
   плеер показывает картинки сам, а склейка рвёт соответствие «номер вопроса
   в очереди = то, что видит оператор». Заголовок, вопрос и варианты на
   картинку не рисовать — их показывает карточка (§5.2, п. 6 требований к
   генератору слайдов).
3. Несколько опросов на одном видео (сначала камера, потом сцены) — законный
   сценарий: один плейлист с непересекающимися чертами либо плейлисты один за
   другим. Ответы каждого лежат в своём `<плейлист>.answers.json`. Правила
   «один плейлист на видео» нет и не вводится.
4. Сколько вопросов задавать за раз, решает оператор, а не формат плейлиста.
5. «Question N/M on this file» в карточке — номер ВНУТРИ файла. Номер в очереди
   пиши в `question` или `name` записи.


- Пишется **перезаписью** (не дописыванием) на паузе, при смене записи,
  на ответе и при закрытии окна; `updated_at` — время последней записи.
- `path` — только путь записи плейлиста; чужие пути (системные,
  `localStorage`, файлы вне плейлиста) в отчёт не попадают: `path: null`,
  `marks: []`, `reached` фильтруется по записям.
- `reached` — по одной строке на запись, `t_sec` = максимальная позиция;
  `marks` — штатные метки текущей записи; `answers` — число вопросов ЭТОГО
  плейлиста с действующим ответом (последний ответ на вопрос): тот же счёт,
  что `answered_question_ids` в `answers.json`, ответы других плейлистов не
  входят. До сборки после 0.26.12 поле считалось по всем маркерам хранилища
  плеера и показывало чужие ответы (339 при «0 из 4» в `answers.json`):
  в 0.26.12 и старше на него не опираться, источник правды — `answers.json`.
- `entry_index: -1`/`path: null` — показ закончился, активной записи нет.

## 5.5. Очередь команд агента: `inbox/` + `ack/` <!-- {#hpdm-s55} -->

С шага 2 ([task:tb_1792536109_79489_5], разведка §6 п.2) агент управляет
показом **файлами**, без порта и сетевой поверхности. Плеер опрашивает
`inbox/` раз в 0,5 с; каждый файл получает ack.

**Где лежит** (`app_data_dir`, macOS) — `~/Library/Application Support/ai.vetka.playerlab/`:

```
inbox/      <id>.cmd.json      ← агент кладёт команду
ack/        <id>.ack.json      ← плеер пишет ответ (по одному на команду)
inbox/done/ <id>.cmd.json      ← исполненные/отвергнутые (аудит, плеер переносит сам)
playlists/  queue_<id>.playlist.json ← inline-подборка из команды open_playlist
```

Точные пути печатает сам плеер: `invoke("command_queue_info")` возвращает
`root/inbox/ack/playlists/done` (для внешнего агента корень — `app_data_dir`
по identifier `ai.vetka.playerlab`; руками путь не угадывать).

**Команда** `<id>.cmd.json` (`id` = имя файла без суффикса, `[A-Za-z0-9._-]`):

```json
{
  "cmd_version": 1,
  "id": "c0ffee-1",
  "verb": "open_playlist",
  "args": {
    "name": "Спорные заминки",
    "by": "Beta",
    "task": "tb_...",
    "entries": [
      { "path": "/Volumes/tempwork/.../Proxies/P1755050.mov",
        "question_id": "q07", "question": "Один ли человек?",
        "hypothesis": "склейка двух людей",
        "in_sec": 812.4, "out_sec": 819.0,
        "choices": ["confirm", "reject", "not_sure"],
        "markers": [{ "kind": "comment", "t_sec": 815.0,
                      "text": "агент: похоже на склейку" }] }
    ]
  },
  "created_at": "2026-10-21T20:00:00Z",
  "expires_at": "2026-10-21T20:10:00Z",
  "author": "Beta"
}
```

- Глаголы: `open_playlist`, `open_file`, `seek`, `play_range`, `next`, `pause`.
- `open_playlist` берёт `args.path` **или** `args.entries[]` (подборка/форма
  вопроса). Inline-записи плеер сохраняет в `playlists/queue_<id>.playlist.json`
  и открывает как обычный вопрос-плейлист — `in`/`out` становятся штатными
  маркерами, ответы ложатся в `<плейлист>.answers.json`, отчёт — в `.session.json`.
  «Рядом» здесь значит рядом с сохранённой копией в app data, а НЕ рядом с
  файлом, который агент держит у себя: для команды `pc-123` это
  `<app data>/playlists/queue_pc-123.playlist.json.answers.json` (суффикс
  целиком `.playlist.json.answers.json`; в других местах манифеста
  `<плейлист>.answers.json` — укороченная запись того же). Читать удобнее
  `player_ctl.py read_answers --cmd pc-123`: он сам находит файл.
- **Комментарии агента** — штатные маркеры в `entries[].markers[]`
  (`kind: "comment"`, `text`), автор берётся из `args.by`/`author`
  (`agent:<кто>`). Своих полей не заводить (§5.1).
- `expires_at` — ISO-8601 UTC; просроченная команда не исполняется.
- Пути: только `$HOME`, `/Volumes`, `$TEMP`, файл обязан существовать
  (canonicalize; те же корни, что у loopback-медиа). Иначе — ack `error`.
- Идемпотентность: команда с уже существующим ack не исполняется второй раз.
  Пока ack нет, плеер повторяет событие (at-least-once) — первый может обогнать
  подписку окна; повтор после падения безопасен, глагол не исполнится дважды.

**Ответ** `ack/<id>.ack.json`:

```json
{ "ack_version": 1, "id": "c0ffee-1", "verb": "open_playlist",
  "status": "done", "at": "2026-10-21T20:00:00.800Z",
  "player_version": "0.26.7",
  "result": { "entries": 43, "questions": 43, "materialized": 43,
              "warnings": [] } }
```

`status`: `done` | `error` | `expired`. У `error` есть `error: {code, message}`.
Коды: `invalid_json`, `invalid_command`, `unsupported_version`, `invalid_id`,
`unknown_verb`, `invalid_args`, `invalid_expires_at`, `path_not_found`,
`path_not_file`, `path_forbidden`, `expired`, `execution_failed`, а у
`open_playlist` ещё `empty_playlist` (в плейлисте нет записей),
`no_questions` (вопрос-плейлист без единого `question_id`) и
`not_a_playlist` (файл не плейлист и не пакет Беты).

С 0.26.7 ([task:tb_1793543005_43420_1]):

- `player_version` — сборка, которая ответила. **Нет поля — плеер старше
  0.26.7**, а также ack со структурной ошибкой (`invalid_json`,
  `path_forbidden`…): их пишет Rust до запуска глагола, и версии в них нет.
- `result` — только у `open_playlist` в статусе `done`: `entries` — записей в
  плейлисте, `questions` — записей с `question_id`, `materialized` — маркеров,
  созданных именно этим открытием (повторное открытие того же плейлиста —
  `0`, это не ошибка). Считается по маркерам, а не по записям: запись с
  `in_sec`/`out_sec` даёт 2 (концы черты `qmat_<qid>_in` и `_out`), запись без

- Открывать нечего — `error` с причиной (`empty_playlist`, `no_questions`),

`done` по-прежнему значит «команда исполнена», а не «человек видит вопросы»:
версию и итог читать из ack, а на старой сборке (поля `player_version` нет)
`done` не доказывает ничего. Что проверить агенту самому — §5.5.2.

### 5.5.1. Ответы оператора: `answers.json` → `ack/<cmd>.answers.json`

## 5.7. Палитра/обмен с индекс-модулем <!-- {#hpdm-s57} -->

UPD 21.10 ([task:tb_1792598687_4475_1]). Владелец отбора, `cut.db` и
экспорта — индекс-модуль `cut-player-mcp`; плеер — показ, маркеры и
ответы человека. Палитра — **необязательный** этап: контракт ниже один
для любой подборки, палитра лишь один из её видов.

Транспорт — файлы/CLI, не MCP и не сеть:
`cut_player_playlist` (модуль → `playlist.json`), `cut_player_export_xml`
(модуль → XMEML), `cut_player_import_answers` (ответы плеера → база).
Плеер читает только `playlist.json` схемы `vetka.cut.question_playlist/1`
(§5); `palette.json` он **не парсит** — это модульный дескриптор.

### Контракт

Обе стороны пишут в артефактах одно и то же:

```json
{
  "contract_version": "1",
  "playlist_schema": "vetka.cut.question_playlist/1",
  "db_version": 9,
  "index_fingerprint": "people/phase.json#<hash>",
  "fps": 25
}
```

`fps` — из индекса/контейнера, не выдуманный: от него считаются кадры
in/out и маркеров. `index_fingerprint` связывает плейлист с версией
индекса, из которой он собран.

### `palette.json` — дескриптор модуля

```json
{
  "items": [
    { "id": "it_0001",
      "ref": { "media": "P1755160.MOV", "in_sec": 26.0, "out_sec": 38.0,
               "person_id": "P112", "phase": "after",
               "phase_piece": [25.75, 48.5] },
      "fav": true, "title": "P112 героиня — готовая укладка" }
  ],
  "bblocks": [
    { "label": "G6d У зеркала — ПОСЛЕ",
      "item_ids": ["it_0001"], "in_sec": 0.0, "out_sec": 12.0 }
  ]
}
```

- `items[].id` — детерминированный от `ref` (тот же ref при пересборке
  даёт тот же id), поэтому ответы и правки переживают пересборку.
- `ref` — **один** объект: `media` — basename исходника, `in_sec`/`out_sec` —
  секунды файла, `person_id`/`phase`/`phase_piece` обязательны,
  `phase_piece` — `[start, end]` секунды файла.
- `fav` — ★, `title` — человеческая подпись; **ни то, ни другое не едет
  в имя клипа**.
- `bblocks[]` — блоки показа: `item_ids` — массив `items[].id` (не refs и
  не объекты), `in_sec`/`out_sec` — координаты таймлайна модуля.

Инвариант блока:

```
b.in_sec == timeline_start(first_item)
         == сумма длительностей предыдущих items + 20 * (число блоков до него)
```

Блок обязан начинаться на границе item. Полный `b.in_sec..b.out_sec` —
только **sequence-маркер** в XMEML; в плеер уезжает точка, не диапазон.
Генератор модуля проверяет инвариант и падает на битом дескрипторе, а не
чинит его пересчётом.

### Маппинг в `question_playlist/1`

| Палитра | Запись плейлиста |
|---|---|
| `ref.media` + исходник | `path` — абсолютный путь, `name` = **basename** |
| `ref.in_sec` / `ref.out_sec` | `in_sec` / `out_sec` (секунды файла) |
| `items[].id` | `question_id` |
| `ref` | `ref = { layer: "palette", id, person_id, phase, phase_piece }` |
| `fav: true` | marker `favorite` на `ref.in_sec` |
| `title` | marker `comment`, `text = title`, на `ref.in_sec` |
| `bblocks[]` | marker `comment`, `text = label`, ровно на `first_item.ref.in_sec` |

**Канон имени (21.10, Beta):** `name` = basename исходника **везде** — в
`entry.name`, в `clipitem/name` и в проекции P. `title` не подменяет имя:
он едет comment-маркером в той же точке, что ★. Так держится правило
оператора «клипы не переименовывать, все пометки — в маркерах»: монтажёр
перелинковывает по именам файлов.

`cut_player_export_xml` (модуль) умеет больше плеера: несколько файлов,
маркеры клипов, ★, блоки **полнодлинными** sequence-маркерами,
Basic Motion (поворот), `name = basename`.

### Ответы

Плеер пишет `<плейлист>.answers.json` и `<плейлист>.session.json` в своей
форме: `question_id`, `verdict`/`choice`/`comment`, `confirmed_by`,
`t_sec`, `in_sec`/`out_sec`. `ref`/`person_id` в ответы **не добавляем** —
это дело модуля: `cut_player_import_answers(playlist, answers)` резолвит
`question_id → ref/person_id/phase`. `t_sec` — секунды файла; таймкод
отвергается. Неизвестный `question_id` или несовпавший `ref` — ошибка
импорта, а не «примерно тот же» момент.

### Проекция P (conformance)

> **P = XMEML без таймлайновых координат и без фильтров; сравниваются
> файловые in/out, имена, маркеры, ★ и порядок.**

P сравнивает: порядок clipitem, `name` = basename, файловые `in`/`out`,
маркеры (`name`, `comment`, `in`, `out`, цвет ★), `question_id`/`ref` в
плейлисте. P **не** сравнивает: `clip <start>/<end>`, `sequence
<duration>`, sequence-маркеры блоков, `<filter>`/Basic Motion. Поэтому
20-секундные паузы модуля и их отсутствие у плеера на P не влияют —
пересчитывать таймлайн не нужно.

### Фикстура и тест

`player_playground/tests/conformance/palette_v01/`:

| Файл | Что это |
|---|---|
| `palette.json` | дескриптор (2 блока, ★, title, повторные фазы) |
| `playlist.json` | выход `cut_player_playlist` по маппингу выше |
| `probe.json` | метаданные источников (длительность, размер, звук) |
| `expected.player.xml` | замороженный выход reference-экспортёра плеера |
| `manifest.json` | контракт, `db_version`, P, sha256 `expected.player.xml` |

`src/lib/paletteConformance.test.ts` строит вход экспортёра из
`playlist.json` + `probe.json`, гоняет `exportPlaylistToXmeml` и сравнивает
с `expected.player.xml` **по P**. Дрейф in/out, имён, маркеров, ★ или
порядка — падение. `expected.player.xml` обновляется только генератором
(не руками) вместе с sha в `manifest.json`.

Полный гейт модуля — `expected.module.xml` (с блоками и Basic Motion),
`expected.answers.json`, `expected_decisions.json` — живёт в фикстуре
`cut-player-mcp`; здесь только проекция плеера.

### Чего плеер намеренно НЕ делает

- не читает `palette.json`, `cut.db`, `orientation.json`;
- не поворачивает клипы (слово оператора 13.10) — Basic Motion только в
  XML модуля;
- не ставит полнодлинные блок-маркеры: маркер записи — точка `t_sec`;
- не заводит сетевой транспорт — только файлы/CLI.

## 6.1. Автор <!-- {#hpdm-s61} --> (работает с 0.25.31, [task:tb_1791583578_64923_1])

## 6.2. Ответы <!-- {#hpdm-s62} --> (reply, работает с 0.25.32, [task:tb_1791585558_31907_1])

Ответ — ОТДЕЛЬНЫЙ комментарий в той же точке со своим автором.
Ссылка на родителя — `reply_to` = marker_id вопроса:

- sidecar/JSON: поле `reply_to: "q03-c1"` рядом с `author`;
- SRT: префикс текста `↳ q03-c1: <текст>` (старый плеер читает как обычный
  коммент — деградация, новый — как ответ);
- в окне Markers ответ — плоской строкой `↳ автор: текст` под родителем;
- в Premiere/XML/EDL — отдельным маркером с пометкой `↳` в имени
  (вложенности Premiere не умеет; в EDL пометка ASCII `>> `, глифы режутся —
  EDL строго ASCII).

## 7. Чтение из MCP-модуля <!-- {#hpdm-s7} -->

Файл — обычный markdown в репозитории, агент индексации
(cut-player-mcp, другой репозиторий) читает его напрямую из git.
Путь зависит от того, откуда сидит агент: из корня репо —
`player_playground/docs/AGENT_DATA_MANIFEST.md`, из папки плеера —
`docs/AGENT_DATA_MANIFEST.md` (оба имени отдаёт `manifest()`:
`dataManifest` / `dataManifestInPlayer`).
Отдельный MCP-тул-указатель (`cut_player_read_manifest`) — follow-up
для Phi, здесь не делается.
